# TreeGrafter Data Components

## PANTHER Data Directory Layout

The `-d` flag points to a PANTHER data directory with the following expected structure:

```
<data_dir>/
  famhmm/
    binHmm            # Concatenated HMM profile database (all families)
    binHmm.h3f        # HMMER binary index files (required for hmmscan)
    binHmm.h3i
    binHmm.h3m
    binHmm.h3p
  Tree_MSF/
    PTHR#####.AN.fasta           # Family MSA (FASTA, 80-char wrapped)
    PTHR#####.newick             # Annotated Newick tree (AN node labels)
    PTHR#####.bifurcate.newick   # Bifurcated Newick tree (for RAxML)
    PTHR#####.tree               # Original PANTHER tree (long IDs)
    PTHR#####.sto                # Stockholm alignment (intermediate)
  PAINT_Annotations/
    PAINT_Annotatations_TOTAL.txt  # Note: intentional typo in filename
    leaf_GO_annotations.tab        # Generated by precompute.pl
    internalnodes_GO_annotations.tab  # Generated by precompute.pl
```

## Data File Formats

### HMM Database (`famhmm/binHmm`)

Standard HMMER3 profile database file containing all PANTHER family HMMs concatenated. Each model is named `PTHR#####.orig.30.pir`.

Used by:
- `treeGrafter.pl` -- passed to hmmscan/hmmsearch
- `autodetect()` -- reads `LENG` fields to estimate database size

The `.h3f`, `.h3i`, `.h3m`, `.h3p` index files are required for hmmscan. If missing, `treeGrafter.pl` runs `hmmpress` to generate them (line 176-183).

**Concern:** The HMM model names include a `.orig.30.pir` suffix (visible in hmmscan output), but the parsing code strips this to extract the `PTHR#####` identifier using `^>> (PTHR[0-9]+)` regex. If the naming convention changes, parsing breaks silently.

### Family MSA (`Tree_MSF/PTHR#####.AN.fasta`)

FASTA-formatted multiple sequence alignment for each PANTHER family. Sequences are named by their AN (Ancestral Node) identifiers.

Format:
```
>AN0
AIKLIAIDMDGTLLLPDHTISPAVKNAIAAARARGVNVVLTTGRPYAGVHNYLKELHMGDYCITYNGALVQKAAG
STVAQTALSYDDYRFLEKLSREVGSHFHALDRTTLTANRDISYYTVHESFPLVFCEAEKMDPNTQFLKVMMIDEPA
ILDQAIARIPQEVKEKYTVLKSAPYFLEILDKRVNKGTGVKSLADVLGIKPEEIMAIGDQENDIAMIEYAGVGVA
MDNAIPSVKEVANFVTKSNLEDGVAFAIEKYVL
>AN1
...
```

**Critical assumptions:**
- Lines are exactly 80 characters wide (except the last line of each sequence)
- `_getAlignLength()` relies on this to compute MSA width: `(num_lines - 1) * 80 + length(last_line)`
- Generated by `sto_to_fasta.py` which hardcodes `wrap=80` (line 107)

**Concern:** If a sequence's last line happens to be exactly 80 characters, and the reader encounters the next `>` header, the calculation is correct. But if the file is regenerated with a different line wrap width, the entire MSA construction breaks silently -- query residues would be placed at wrong MSA positions.

### Newick Trees

Two Newick tree variants per family:

**`PTHR#####.newick`** -- Annotated tree with `AN####` internal node labels. Used by `commonancestor()` to find the lowest common ancestor of graft placements.

**`PTHR#####.bifurcate.newick`** -- Strictly bifurcating version of the tree (no polytomies). Required by RAxML which cannot handle multifurcating trees. Generated by `precompute.pl` via `tobifurcate()`, or post-processed by `fix_bifurcate_files.py`.

Format: Standard Newick with `AN####` as both leaf and internal node labels.

```
((AN0:0.1,AN1:0.2)AN2:0.3,(AN3:0.1,AN4:0.2)AN5:0.3)AN6;
```

**Concern:** `fix_bifurcate_files.py` strips the outermost parentheses from bifurcate Newick files (`tree_text[1:len(tree_text)-2] + ";"`). This transformation assumes the tree is rooted and enclosed in a single outer pair of parentheses. If applied to an already-fixed file or a file with a different structure, it will corrupt the tree.

### Annotation File (`PAINT_Annotations/PAINT_Annotatations_TOTAL.txt`)

Tab-separated file mapping PANTHER tree nodes to their functional annotations.

Format:
```
PTHR#####:AN##	SF:PTHR#####:SF##;NAME:protein name;GOA:GO:0000000;GO:0000001;PC:PC00000;
PTHR#####:root	SF:PTHR#####:SF##;NAME:protein name;GOA:GO:0000000;
```

Columns:
1. Node identifier: `PTHR_family:AN_node` or `PTHR_family:root`
2. Annotations: semicolon-delimited string containing:
   - `SF:PTHR#####:SF##` -- Subfamily assignment
   - `NAME:protein name` -- Protein name
   - `GOA:GO:#######;GO:#######;...` -- GO annotations
   - `PC:PC#####;` -- Protein class (optional)

Loaded into `$options->{annotations}` as a simple key-value hash during `processOptions()`.

**Concerns:**
- The filename typo (`Annotatations` with double 'a') is intentional and hardcoded in both the main script and precompute script. Renaming the file to the correct spelling will break the pipeline.
- Annotation values are stored as raw strings and split by the CGI wrapper using whitespace (`split(/\s+/,$annotations)`, cgi-bin line 144), assuming a specific internal structure (SF, then GOA, then PC separated by spaces). If annotation values contain spaces, parsing breaks.

### Generated Leaf/Internal Annotation Files

`precompute.pl` generates two additional tab-separated files:

**`leaf_GO_annotations.tab`**:
```
PTHR#####:AN##	SF:PTHR#####:SF##  GO:0000000;GO:0000001;  PC00000;	long_gene_id
```

**`internalnodes_GO_annotations.tab`**:
```
PTHR#####:AN##	SF:PTHR#####:SF##  GO:0000000;GO:0000001;  PC00000;	PTN_id
```

These files use double-space as field separator within the annotation column, mixing tabs and spaces. This makes them difficult to parse reliably.

**Concern:** The `processinstance()` function in `precompute.pl` (line 224-243) handles GAIN/NOT propagation of GO annotations down the tree. A GO term with a NOT qualifier cancels a GAIN. But the counting mechanism (`$store{$key}++` / `$store{$key}--`) would fail if a GO term is gained more than once or negated more than once along a path, since it uses a simple counter rather than boolean state.

## Input Format

### FASTA Input (`-f`)

Standard FASTA format. Sequence IDs can contain any characters but non-word characters (`[^\w]`) are replaced with underscores in the output and in temp filenames.

Example:
```
>STRCO|Gene=CAB44512|UniProtKB=Q9XAS3
DRTAYSLVATDLDGTLLRGDDTVSDRSLAALARVAGAGARHLVVTGRPA...
```

Becomes `STRCO_Gene_CAB44512_UniProtKB_Q9XAS3` in output.

**Concern:** The ID sanitization (`s/[^\w]/\_/g`) is applied in multiple places independently (`_generateFasta` line 552, `_runRAxMLAndAnnotate` line 580). If a sequence ID is sanitized differently in different contexts, the pipeline could fail to match temp files to their queries.

### Precomputed HMMER Output (`-hmmer`)

Full HMMER text output from either hmmscan or hmmsearch. The user must also specify `-algo hmmscan` or `-algo hmmsearch` to tell the parser which format to expect.

**Concern:** There is no validation that the provided HMMER file matches the specified algorithm. Providing an hmmscan output with `-algo hmmsearch` (or vice versa) will silently produce wrong or empty results.

## Output Format

### Main Output (`-o`)

Tab-separated, one line per query sequence:

```
gene_id\tPTHR_family\tannotations\tgraft_point
```

Fields:
1. **gene_id**: Input sequence ID with non-word chars replaced by underscores
2. **PTHR_family**: Best-matching PANTHER family (e.g., `PTHR10000`)
3. **annotations**: Annotation string from `PAINT_Annotatations_TOTAL.txt` (e.g., `SF:PTHR10000:SF8;NAME:Sugar phosphatase YidA;GOA:GO:0016311;GO:0016791;`)
4. **graft_point**: Tree node where the query was placed (e.g., `PTHR10000:AN42` or `PTHR10000:root`)

Example:
```
STRCO_Gene_CAB44512_UniProtKB_Q9XAS3	PTHR10000	SF:PTHR10000:SF8;NAME:Sugar phosphatase YidA;GOA:GO:0016311;GO:0016791;GO:0005737;	PTHR10000:AN42
```

**Concerns:**
- Output order is nondeterministic (depends on Perl hash iteration order for `$matches`).
- There is no header row.
- Queries that match a PANTHER family but have no annotations produce a warning to stderr but no output line -- they silently vanish from results.
- The "root" graft point is used both as a legitimate placement (query is an outgroup to all family members) and as a fallback when RAxML fails. These cases are indistinguishable in the output.
- The annotation column can be `undef` if the lookup fails, which prints as empty string in Perl.

### CGI XML Output

The CGI wrapper returns XML:
```xml
<Response>
  <GOAnnotations>GO:0016311;GO:0016791;</GOAnnotations>
  <GraphPointNode>PTHR10000:AN42</GraphPointNode>
  <MSA>>query_uuid\nSEQUENCE...</MSA>
  <SF>SF:PTHR10000:SF8</SF>
  <PCAnnotations>PC00000;</PCAnnotations>
</Response>
```

**Concern:** The MSA content is embedded raw in XML without escaping. Sequence data containing `<` or `>` (unlikely but possible in headers) would break XML structure. The `>` in FASTA headers is not escaped.

## Intermediate/Temporary Files

During pipeline execution, the following temp files are created under `$tmpDir`:

| File | Purpose |
|---|---|
| `<queryid>.<pthr>.fasta` | Combined query + family MSA for RAxML input |
| `<pthr>_<queryid>_raxml<pid>/` | RAxML working directory |
| `RAxML_portableTree.<pthr>.jplace` | RAxML placement output (JSON) |
| `RAxML_info.<pthr>` | RAxML run information |
| `RAxML_labelledTree.<pthr>` | RAxML labelled tree output |
| `<fastafile>.<algo>.out` | HMMER output (in input file's directory, not tmpDir) |

**Concerns:**
- The HMMER output file is written next to the input FASTA file, not in tmpDir. This means `-k` (keep temp files) doesn't control its cleanup, and running two pipelines on the same input file concurrently will cause a race condition.
- `$tmpDir` defaults to `undef` if not specified via `-t`. The code attempts `mkdir` on `undef` (line 105-106), and all temp file paths include `undef` as a path component, which creates files in the current directory with `undef` in the name.
- Temp cleanup uses `rm -rf $tmpDir/*` (line 468), which runs between each query. If one query's RAxML output is needed for debugging but another query runs after, the output is already gone.

## Data Preprocessing Pipeline

To prepare PANTHER data for TreeGrafter, three scripts run in sequence:

```
[PANTHER Library Release]
        |
        v
gettreesandmsf_hpc.pl    # Extract trees + run hmmalign -> .tree, .sto files
        |
        v
sto_to_fasta.py           # Convert .sto to .AN.fasta files
        |
        v
precompute.pl             # Generate annotation files + .newick + .bifurcate.newick
        |
        v
fix_bifurcate_files.py    # Fix outer parentheses in .bifurcate.newick (if needed)
        |
        v
[TreeGrafter Data Directory ready]
```

**Concerns:**
- This pipeline is not documented anywhere in the repository except implicitly through the scripts themselves.
- `gettreesandmsf_hpc.pl` and `sto_to_fasta.py` both require SLURM, making data preprocessing impossible on a local machine without modification.
- `precompute.pl` requires an external `HAIMING::ToNewick` Perl module not included in the repository.
- The raw PANTHER library files (annotation.dat, node.dat, etc.) required as input to `precompute.pl` are in a different format than the PANTHER FTP download, with no documentation of how to obtain or structure them.

## Data Versioning

- The code contains remnants of PANTHER version-specific paths (PANTHER12.0, PANTHER13.1, PANTHER14.1) in comments throughout.
- The current code is version-agnostic (uses generic directory names like `famhmm/binHmm`, `Tree_MSF/`).
- There is a TODO at line 109 of `treeGrafter.pl`: "Deal with different releases, hardcoded to 12.0" -- this has been partially addressed but the comment remains.
- The README references `treeGrafter1.01_supplemental.tar.gz` from the PANTHER FTP site, which is specific to PANTHER 12.0 data. The relationship between this tarball and newer PANTHER releases is undocumented.

## Data Integrity Concerns

1. **No checksums or validation**: The pipeline validates file existence and non-zero size but never validates file content integrity. Corrupted HMM databases, truncated FASTA files, or malformed Newick trees will produce wrong results silently.

2. **Cross-file consistency**: The annotation file, MSA files, and tree files must all reference the same set of AN nodes. No validation ensures this consistency. If the annotation file references a node not present in the tree, `commonancestor()` will fail.

3. **Filename conventions**: The entire pipeline relies on rigid filename conventions (`PTHR#####.AN.fasta`, `PTHR#####.bifurcate.newick`, etc.). These are implicitly defined by the preprocessing scripts and assumed by the main pipeline, but never documented or validated as a schema.
